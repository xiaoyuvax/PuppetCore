# 我让 Agent 给自己写了一个全自动调试工具

> 一个 AI Agent 在开发一个 WinForms 应用时，顺手给自己造了一套 HTTP 调试端点；造完之后，它开始用这套端点调试宿主应用，发现端点不够用，于是回头改这套端点的源码，重新编译，再继续调试。整个循环里，我只负责在它问"要不要试一下"的时候说"继续"。

这个工具叫 **Puppet.Core**，MIT 协议，C# 实现，已发布到 NuGet。但它的真正用法不是"安装一个库"，而是**把一份文档丢给你的 Agent**。

---

## 起点：GUI 程序的测试，是个老大难

给命令行程序写测试是容易的：调函数、断言返回值。给 Web 服务写测试也不难：发请求、看响应。

但给一个**编译后才能跑的桌面程序**写自动化测试，历史上基本只有一条路：

**UI Automation** —— 截屏找像素、控件树定位、合成鼠标键盘、抢焦点。

这条路的痛苦，做过的人都懂：

* 界面一改版，选择器全废；
* 焦点被别的窗口抢走，脚本就瞎了；
* 多显示器 / 高 DPI 下坐标换算能让人怀疑人生；
* 最要命的是，它只能表达"点哪里"，表达不了"要做什么"。

于是大家默认接受了一个现实：**GUI 程序的自动化测试，就该是脆弱的。**

Puppet.Core 的出发点是一句反问：

> 如果 Agent 本来就在源码里、本来就在编译循环里，为什么非要绕到屏幕外面去"看"这个程序？

---

## 一个反直觉的决定：别碰 UI

Puppet.Core 的做法是给宿主进程**开一个内嵌的 HTTP 端点**，让 Agent 直接读状态、调方法：

```bash
# 看看这个窗体能干什么
GET  /agent/describe?name=TaskBoardForm&format=md

# 读一个属性（单属性粒度，不序列化整对象）
GET  /agent/get?path=SelectedTask.Title

# 调一个方法 —— 这就是"点保存按钮"的等价物
POST /agent/invoke?name=TaskBoardForm&method=SaveAll
```

宿主侧的接入成本，是实现 3 个属性：

```csharp
public class TaskBoardForm : Form, IPuppet
{
    public string AgentAccessKey  => PuppetKeyVault.Current;
    public ILog    AgentLog       => _log;
    public string  AgentInstanceName => "TaskBoard";
}
```

反射会自动生成能力描述（`/agent/describe`），JSONPath 会读到任意深度的运行时状态（`/agent/state?path=a.b.c`），`/agent/invoke` 会阻塞等待 `Task` 完成、并自动把跨线程调用切回 UI 线程。

**关键不在于这些端点，而在于它们不走哪条路。**

---

## 三条核心原则

### 一、不使用用户侧的 UI 接口 —— 指令从不进入 GUI 通路

Puppet 的所有操作都**不经过**截屏、不经过合成输入、不依赖控件句柄和焦点。它直接调用业务方法、直接写属性、直接触发事件。

这不是为了"绕开 UI 更高级"，而是因为一个更朴素的事实：**Agent 和用户不共享同一条操作流程**。

由此得到一串免费的好处：

| 性质 | 说明 |
|------|------|
| **不打扰用户** | Agent 的指令不抢焦点、不遮挡窗口、不与用户的手冲突。你可以在同一台电脑上照常操作**其他**应用，Agent 在旁边跑它的测试。注意方向性：是"Agent 不打扰你"，不是"互不干扰"——同一个被测应用上的人工操作（比如顺手关掉窗体）仍会打断 Agent 的测试，毕竟它们共享同一个进程 |
| **稳定** | 界面改版、按钮挪位置、换个皮肤，Agent 的指令一条都不用改——它调的是 `SaveAll()`，不是 `(317, 42)` 那个像素 |
| **可并发** | 多个 Agent 可以同时工作，靠 `SiteLock`（站点读写锁）与 `AgentBook`（心跳注册表）协调，不会互相踩 |
| **可回归** | 动作名是稳定契约，昨天的调试脚本今天还能跑 |
| **可审计** | 每一步都是"调用了哪个方法、传了什么参数"，不是"在屏幕上点了哪里" |

需要"看一眼界面"时，它走的是**应用内部截屏**（WinForms `Graphics.CopyFromScreen` 之上的封装 / WPF `RenderTargetBitmap` / 页面截图需用户显式勾选授权开关）——拿到的是应用自己绘制的像素，不拦截输入、不遮挡界面、多屏下也不会生成整屏大图。

一句话：**Puppet 对 UI 的所有感知都来自应用内部，所有操作都来自代码通路。UI 只是给人看的，不是给 Agent 用的。**

### 二、Puppet 自己完成宿主应用的调试与测试

集成之后，调试循环长这样：

```
Agent 读 DEVELOPMENT.md（它就是 Skill 说明书）
  → GET  /agent/registry              确认实例已注册
  → GET  /agent/describe?format=md     看能力，规划操作序列
  → GET  /agent/get?path=...           读状态，确认起点
  → POST /agent/set   {path,value}     模拟用户输入（会触发对应事件）
  → POST /agent/invoke?method=...      模拟用户操作，推进到测试现场
  → 轮询就绪标志 → 再读状态 → 断言
  → 出错？GET /agent/logs、/agent/usage 看日志与调用统计
```

这里有一条**刻意写死的纪律**（在 `DEVELOPMENT.md` 里，Agent 必读）：

> **优先通过宿主工程已有的、面向用户的代码路径完成测试。首先不要编写 `XxxForTest()` 之类的调试专用方法。**

只有当 Agent 拿出**确切证据**表明既有路径走不通时，才允许加一个测试钩子，而且这个钩子必须打上 `[PuppetTest]` 标记，任务完成后清理掉。

这条纪律的收益是隐蔽但巨大的：**因为不能写旁门，Agent 被迫把测试走成真实用户路径。** 它测的永远是用户真正会走的那条代码，而不是一条专门为测试开辟的、没人维护的岔路。发现模态对话框会堵住测试？那不是加钩子绕过去，而是把事件处理器拆成 UI 层（留对话框）和业务层（Agent 直接调），这是本来就该做的重构。

配套的还有接口分野：**操作类接口**（模拟用户流程）与**日志类接口**（客观观测）分开管理，各自有明确的引入、稳定、交付清理节点——调试期临时插的观测日志，测完就删。

### 三、Puppet 自己迭代 Puppet 框架

这是整个项目最有意思的部分。

Puppet.Core 提供两种工作方式，对应两种不同的"成长预期"：

**方式一：源码导入 —— 可塑性高，自己长成自己的样子。**
把 `Puppet.Core/` 目录整个放进宿主工程，Agent 就拿到了框架源码的修改权。它不再是"用一个库"，而是"养一个库"：调试宿主时发现缺能力，就改框架、重新编译、继续调试。框架最终长成什么样，取决于这个工程经历过什么——每个宿主项目都会把框架揉捏成最贴合自己需求的形状。可塑性极高，代价是你要把它纳入自己的编译与维护。

**方式二：NuGet 包 —— 相对固化，但开箱即用。**
`dotnet add package Puppet.Core`，用上的是发布版本里积累的开发经验：每一项能力都是在本仓库自己的 TestGround 试验场上，被真实调试任务反复锤炼、验证过才发出来的。它不会为你的项目现场演化，相对固化，但普通场景的自动化调试需求完全够用。方法论文档 `DEVELOPMENT.md` 随包分发，Agent 照样能拿到完整的"武功秘籍"。

怎么选：项目周期长、需求刁钻、想让 Agent 拥有框架的迭代权 → 源码导入；想低成本接入、场景常规 → NuGet 包。而且这不是单向选择——完全可以先用 NuGet 起步，等哪天需求长到包接不住了，再切到源码导入。

源码导入模式下，自我迭代的循环是这样的：

1. Agent 调试宿主应用，发现缺一个能力（比如"我需要截个图确认渲染结果"）；
2. Agent 打开 Puppet.Core 源码，加一个合成方法 `CaptureAction`，两处同步注入（`describe` 与 `invoke` 各自独立反射，必须两边都补）；
3. 重新编译宿主；
4. 回到第 1 步，用新能力继续调试。

**框架的开发者、测试者、使用者，是同一个 Agent。**

防臃肿的机制也是运行时的：`GET /agent/usage` 给出每个能力类别的调用次数与错误数，Agent 据此判断哪些能力从没人用、该删。框架不会因为"以后可能有用"而膨胀——**不被使用的能力，会被清理掉**。

还有一层更安静的自我演化：`[PuppetHint]`。Agent 某次踩到一个坑（"这个属性改了会触发重绘，频繁调用卡 UI"），就地打一个标记，随 `/agent/describe` 一起返回给下一个读它的 Agent。坑点在代码里沉淀，不需要人去维护 wiki。

## 多 Agent 同场作业：签到板 + 工具借还登记

一个较少被谈论的现实：调试现场往往不止一个 Agent。可能一个在驱动保存流程做回归，一个在读日志找报错规律，还有一个在采样性能。谁来保证他们不互相踩？

Puppet.Core 内置了一套多 Agent 协调机制，三张注册表各管一摊：

* **PuppetRegistry** —— "被调试的东西在哪/是谁"：所有 `IPuppet` 实例的注册表，Agent 动手前先查它确认目标在场。
* **AgentBook** —— 签到板："谁在调试、想干什么、还要多久"。每个 Agent 带 `Id` / `Purpose` / `Operation` / 预估等待秒数登记，所有 `/agent/*` 调用自动续心跳（5 分钟超时自动清退，不用专门保活）；想关宿主进程前，先 `POST /agent/book/release` 问一句"还有别人在吗"，拿到 `canShutdown` 再动手——**正常关闭是一场握手，不是单方面拔电源**。
* **SiteLock** —— 工具借还登记：站点是字符串路径（`"Form1.btnSave"` 一个按钮、`"Form1.*"` 整个窗体、`"*"` 整个实例），`Read` 共享、`Write` 独占、可重入。它刻意做成**建议性锁**：框架不拦截未加锁的调用，靠 Agent 自愿遵守——因为拦死的锁比没锁更糟。

最舒服的一点：协调信息（`agentId` / `agentPurpose` / `site` / `lockMode`）全部是 `/agent/*` 的透传参数，**随每次业务调用捎带**，不为协调多发一个请求。

## 让它真的能用，靠的是一些不浪漫的细节

光有原则是跑不起来的。真正让这套东西在真实工程里活下来的，是几条踩出来的经验，全部写在 `DEVELOPMENT.md` 里：

* **模态框永不阻塞。** `MessageBox.Show` 会挂死 UI 线程和 Web 调用线程。框架在请求入口统一 `DialogBroker.Push(null)`，Agent 上下文里的模态一律按安全默认（Cancel/No）自动应答；**人工界面操作不走这条通道，原生模态行为不变**。修复前同一路径挂死到 HTTP 超时，修复后 0.17s 返回。
* **不序列化整对象。** 对含 WebView2 / Form / 事件处理器的复杂对象整图序列化会直接崩进程，所以优先 `/agent/get?path=<单个>`，深路径 `a.b.c` 逐层走。
* **就绪要轮询。** 异步 UI 流程调用完不要立刻读下一个状态，轮询 `IsReady` 之类的标志。
* **测试要能自证。** 每个 TestGround 工作台都带 `--self-test`，退出码 0/1/2 三态，Agent 可以自己跑、自己判断、自己迭代。

四个 **TestGround** 试验场（WinForms 任务看板、Console 支出账本、WPF 阅读清单、ASP.NET Core 库存预留）是框架的练兵场：覆盖四类典型宿主形态，Agent 在上面持续工作，发现问题、驱动修复，把经验沉淀回各自的 `AGENTS.md` / `DEVELOPMENT.md`。原则只有一条——**框架改动必须由可复现的问题证据驱动，不投机性加功能。**

## 另一个野心：让用户的 Agent 也来操控应用（B 面向，不完善，欢迎试用）

前文说的都是 **A 面**：开发期的 Agent 拿着源码调试宿主。Puppet.Core 还留了另一个门面——**B 面向**（`/appagent/*`），场景完全不同：

应用编译发布后，终端用户对着自己的个人 Agent 说一句"帮我把这批过期任务都归档"，Agent 就以语义化动作驱动应用完成操作——不截屏、不模拟点击、应用在发布形态下零改动即可被发现。

实现思路叫 **Actionize 范式**：事件处理器里的业务逻辑提炼成 `public` + 成败返回（`bool` / `OperationResult`）的方法，就**自动**进入能力目录（`GET /appagent/manifest`）；动作文案优先取自 UI 上已有的文字（按钮、菜单），用户看到的能力名就是界面上写的那个词。带模态对话框的操作经预答表代答，永不阻塞；破坏性操作强制 `confirm`。发现也是零配置：Agent 枚举 `%LOCALAPPDATA%\Puppet.AppAgents\` 下的档案，就能找到本机所有启用了 B 面的应用，OS 用户隔离代行授权。

诚实地说，B 面向**还不完善**：Actionize 只收录"已写成 public 业务方法"的动作，而大量用户操作仍埋在私有事件处理器里；"UI 控件 ↔ 动作"的完备性门禁也还没建立。它现在是**能用的试用版，不是成品**——`TestGround.Winform` 里有 A/B 双面向并存的完整演示，欢迎踩坑，踩到的坑欢迎反馈。

## 换一门语言？把 DEVELOPMENT.md 丢给你的 Agent

这是我认为最值得开源社区试一试的部分。

Puppet.Core 的**可移植内核不是代码，是 `DEVELOPMENT.md`**。那份文档从第一行起就写明了阅读对象是 AI Agent 而非人类开发者，包含：核心接口、集成模式、调用约定、安全边界、操作/日志分野、"优先走既有路径"的纪律、多 Agent 协调协议、以及一整章实战踩坑记录。

它本质上是一份 **Skill 说明书**。移植到别的语言，流程是：

```
1. 新建一个项目（Puppet.Py / Puppet.Java / Puppet.Go / Puppet.Rs……）
2. 把 DEVELOPMENT.md 放进去
3. 对你的 Agent 说："读这份文档，按它的原则，为本项目实现这套调试端点"
4. 让它在真实调试中迭代这个工具本身
```

文档里已有一段给移植者的免责声明，写得很宽松：

> 本框架不绑定 .NET，也不要求移植者复刻本指南的端点/鉴权/响应形状——本指南只是一个"想法"的范例。语言、内部设计、甚至协议细节均由实现者自主决定，移植方也可以直接更新本指南。

也就是说，你需要复刻的是**原则**，不是协议：

1. **不走用户侧 UI 通路**，不与用户抢焦点、不共享操作流程；
2. **Agent 走宿主已有代码路径**完成调试，不为测试开旁门；
3. **Agent 负责维护并迭代这套框架本身**，能力使用率驱动清理。

C# 版本的源码在这里，随时可以对照——反射对应你语言的内省，`WebServerBase` 对应你的 HTTP 栈，WinForms 控件树对应你的 GUI 工具包。

## 现状（不含宣传成分）

* **A 面（Agent 自调试闭环）已成熟**：状态可读到单属性粒度，`invoke` 等待 `Task`，跨线程自动回 UI 线程，实测可稳定驱动完整业务流程。
* **B 面（用户代理操作）**：即上文的试用版——能力可用，覆盖度与完备性门禁是主要缺口，文档里老老实实写了缺口在哪、怎么扫。
* 框架的开发与验证全程由 Agent 完成，人类只做最终的视觉验收与版本发布决策。

## 试试看

**在你的 C# 项目里：**

```bash
dotnet add package Puppet.Core
```

然后让你的 Agent 读 `README.md` 和 `DEVELOPMENT.md`（装包后在 `~/.nuget/packages/puppet.core/<version>/DEVELOPMENT.md`，或运行中请求 `GET /agent/docs` 拿到与程序集版本一致的那份），并指示它把读取入口写进你工程的 `AGENTS.md`。宿主只需实现 `IPuppet` 的 3 个属性，两行代码起服务器：

```csharp
PuppetKeyVault.SetKey("your-secret");
new PuppetWebServer().Start("0.0.0.0:9090");   // WinForms 加 .UseFormControls()
```

想要源码导入模式？直接把仓库里的 `Puppet.Core/` 目录拷进你的解决方案、加个项目引用，剩下的迭代权就交给 Agent 了。

**在别的语言里：**

克隆本仓库，把 `DEVELOPMENT.md` 交给你的 Agent，让它按上面四步做出你语言的版本——然后把这个仓库的 issue / PR 打开，我想看它会长成什么样。

**想试试 B 面向？**

跑起 `TestGround.Winform`（任务看板），它同时开着 A/B 两个门面；然后给另一个扮演"终端用户"的 Agent 下达自然语言指令，看它经 `/appagent/*` 把操作一步步做完。

**在你已有的 Agent 工作流里：**

即使你不用这套端点，也值得试一次那个纪律——**禁止 Agent 写 `XxxForTest()`，逼它走用户真实路径**。这一条不依赖任何框架，但可能比框架本身更管用。
